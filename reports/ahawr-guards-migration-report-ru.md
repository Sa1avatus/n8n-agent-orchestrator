# Отчёт миссии ahawr-guards-migration

Отчёт написан оператором: задача T026 (отчёт) не прошла ревью за четыре попытки, закрыта вручную. Факты взяты из `docs/guards.md`, `claude-runner/docs/guards-notes.md` (разделы Migration baseline, heartbeats, dry-run, final) и из состояния репозитория.

## 1. Главное

- Сделано и проверено тестами: код стражей внутри контейнера `ahawr-dashboard`, пробный режим (dry run), запуск через хост-лаунчер, heartbeat-файлы хостовых watcher-ов, скрипты вывода из эксплуатации и отката, документация.
- НЕ сделано (так и задумано миссией): ничего не включено, не перезапущено, не остановлено и не отправлено. Compose-патч и патч старта watcher-ов лежат как предложения (`guards-compose.patch`, `guards-start.patch`), хостовые `queue_watch.py` и `orphan_guard.py` работают как раньше. Переключение выполняет оператор отдельным окном.
- Без флага `DASHBOARD_GUARDS` поведение не меняется: `GET /api/guards` отвечает `enabled: false` с прежним телом; все новые стражи по умолчанию выключены.

## 2. Куда ушло каждое дело хоста

Обозначения: CG страж в контейнере, HB остаётся на хосте и пишет heartbeat, HL хостовый лаунчер, RT выводится.

| Скрипт | Дело | Куда |
|---|---|---|
| queue_watch.py | уведомления о миссиях (не завершена с последним ревью, завершена, ALERT, очередь остановлена/завершена, маркеры Docker) | CG `mission_notice` (QUEUE_NOTICES) |
| queue_watch.py | лимит 20 уведомлений в час, повтор | CG (состояние в памяти, при рестарте дашборда теряется) |
| queue_watch.py | уведомление о простое 1200 с | CG `idle` (QUEUE_IDLE) |
| queue_watch.py | перезапуск очереди (лимит 4 в час, нет выполнений) | CG пишет запрос, HL запускает (QUEUE_RESTART) |
| queue_watch.py | выгрузка архива thinking раз в 6 часов | CG (THINK_ARCHIVE) |
| queue_watch.py | основной цикл, лог, `ensure_relay`, `slot_loop_running` | RT |
| tg_relay.py | long poll, пересылка в webhook n8n, смещение, меню команд, backoff | CG `tg_relay` (TG_RELAY) |
| orphan_guard.py | поиск осиротевших процессов и завершение | CG (ORPHAN_PROCESS), нужны два новых маршрута раннера `GET /v1/processes` и `POST /v1/processes/{pid}/terminate` |

## 4. Решение «лаунчер или задача планировщика»

Выбран запрос-ориентированный хостовой лаунчер (вариант A): решение о перезапуске принимает страж контейнера (он видит раннер и хранилище), хост только выполняет проверенный запрос из файла `queue_restart.req` (запись через `.tmp` и rename, JSON из трёх полей, срок запроса, лимит 4 в час, повторная проверка отсутствия выполнений n8n). Задача планировщика опрашивала бы вслепую и разносила правила по двум местам.

## 5. Результат пробного прогона (dry run)

Миссия `ahawr-worker-attempt-chain`, окно 379 строк лога. Страж дал бы 5 уведомлений; `queue_watch.py` отправил 12: 5 совпало, 7 уведомлений о перезапуске очереди определяются по таблице процессов и в логе их нет (страж их из логов не воспроизводит). Различия: у 3 уведомлений о незавершённой миссии в реплее нет блока «последнее ревью» (в реплее пустой источник событий, в работе его даёт `_last_review`); задержки 26–55 с задаёт цикл отправителя. Расхождение в логике простоя: `queue_watch.py` считает «в работе» и queued, страж только running, поэтому при очереди без запущенных задач они могут расходиться. Окно dry run перед боевым режимом остаётся обязательным.

## 7. Риски и открытые пункты

1. Compose и env для `ahawr-dashboard` (монтирование ops только для чтения, каталоги запросов и состояния на запись, URL webhook) меняют Docker-топологию: нужен ваш выход, патч подготовлен.
2. Новые маршруты раннера для orphan-стража и доступ к Postgres n8n (число выполнений, chat id) не реализованы: эти дела останутся на хосте, пока не будут сделаны.
3. Состояние стражей (лимиты, ожидающие уведомления) хранится в памяти, при рестарте дашборда теряется.
4. Токен Telegram в контейнер идёт из `DASHBOARD_TELEGRAM_BOT_TOKEN`, значения не выводятся; ротация токена остаётся в планах.
5. Два relay с одним токеном опрашивать Telegram одновременно не могут: хостовый `tg_relay` и страж останавливаются в одном шаге.
