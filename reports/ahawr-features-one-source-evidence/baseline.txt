4. HOW EACH INPUT FORM IS HANDLED TODAY

  Empty value ("" or None):
    _parse_text, features_config.py:76-78  source = (text or "").strip(); if not source: return {}
    -> the sparse map stays empty, so _resolve_features (features_config.py:102-109) fills every feature from
       FEATURE_DEFAULTS; parse_features returns the full default set with errors == [].
    At the route the text is coerced to "": _features_text, board_api.py:305-309 (text = body.get(key, ""),
    a non-string raises ValueError); GET returns row.get("features_json") or "" (board_api.py:1941, 2014).
    Pinned by tests/test_features_config.py:41-47 (None and "") and tests/board_features.test.js:33.

  {} (a literal empty object):
    _parse_text, features_config.py:79-86: json.loads succeeds, isinstance(parsed, dict) is true, the loop at
    :88-95 iterates zero items -> sparse {} -> same full defaults as the empty case. A non-object (a number,
    an array) errors at :84-86 with "{column}: must be a JSON object".

  Absent column (the hermes_config row or the mission config has no features key):
    board_api.py:95   (store.hermes_config() or {}).get("features_json")  -> None, passed to parse_features
    board_api.py:90   (store.mission_config(mission_id) or {}).get("mission_features_json") -> None
    board_api.py:1941, 2014  the GET routes return "" for a missing column, so the UI never sees None.
    _parse_text treats None exactly like "" (features_config.py:76-78). In runs.py:43 and api.py:27 the same
    parse_features is called on the stored text.

  Partial object (only some parameters, e.g. {"adaptive_split": {"enabled": true}}):
    _check_feature, features_config.py:63-72: every key of the body is checked against FEATURE_DEFAULTS[feature]
    (:68-69 unknown parameter -> error), and only the known ones land in `accepted` (:71), so `accepted` holds
    exactly the parameters the operator wrote. Missing parameters are then filled from FEATURE_DEFAULTS in
    _resolve_features (:102-109). Cross-parameter consistency is only checked on the merged result in
    _check_limits (:112-118): max_tasks_hard must be >= max_tasks; a partial {"max_tasks_hard": 5} alone is
    accepted and merged with the default max_tasks 15 (the limit error then appears, naming the merged value).

  Mission override (mission_features_json vs features_json):
    _resolve_features, features_config.py:98-109 - the spread order is defaults, then global, then mission:
    mission_features.get(feature, {}) is spread LAST, so a mission parameter wins per parameter, not per feature
    (a mission that writes only {"max_splits": 2} keeps the global values of the other parameters of adaptive_split).
    Validation of the pair happens before saving: board_api.py:2031 validate_features_json(global_text, text),
    where global_text is read again at :2030; the board-side reader applies the same merge through
    _feature_enabled (board_api.py:85-103), and an invalid stored JSON leaves every flag off (:97-103).
