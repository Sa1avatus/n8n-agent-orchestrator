# Отчёт по миссии `ahawr-rag-quality` (2026-10-28)

Миссия выполнена: все 20 задач завершены. Улучшения точности поиска она не дала: ни один из проверенных вариантов не прошёл порог. Зато теперь качество поиска измеряется офлайн, и мы знаем, куда не стоит тратить время.

## Цель

На 15.10.2026 по живым прогонам точность поиска Worker была 8,6 %, полнота 16,9 %. Скорость поиска уже исправили (121 с → 0,4–1,7 с), качество выдачи не менялось. Цель миссии: поднять точность без потери полноты и без роста задержки выше 5 с, и научиться измерять качество офлайн.

## Что сделано

| Часть | Результат |
|---|---|
| 1. Офлайн-набор | `retrieval-service/eval/data/real_queries.jsonl`: 90 реальных запросов (45 Worker, 45 Reviewer), только запрос, роль и пути, без секретов. Команда `ahawr-retrieval-eval run --dataset real` выдаёт precision, recall, MRR, p50/p95. |
| 2. Эксперименты | Около 20 вариантов (форма лексического запроса, веса слияния и RRF k, лимит фрагментов с файла, размер фрагмента, заголовок с путём, порог отсечения), каждый за параметром окружения, по умолчанию поведение прежнее. Таблица в `docs/rag-quality.md`. |
| 3. Search gate | Флаг `AHAWR_SEARCH_SKIP_PATH`: поиск пропускается, если запрос сам является существующим путём. По умолчанию выключен, есть тесты, формулировка правила для Worker готова. |
| 4. Метрики `usage` | `usage` показывает precision и recall по роли, типу запроса и дням, с тестами. Процедура сравнения до и после на живых прогонах описана в `docs/rag-quality.md`. |

## Результаты экспериментов

Порог принятия: precision@5 минимум +20 % (до 0,2507), recall@8 не ниже базового минус 0,03, p95 до 5 с.

База на заглушке-эмбеддере (hashing): precision@5 0,209, recall@8 0,203, MRR 0,299, p95 226 мс.

**Вердикт: ни один вариант не принят.** Лучший (веса слияния 1,5/0,5, RRF k=30, фрагменты до 40 строк) дал precision@5 0,229 (+9,6 %), но recall@8 упал до 0,157, ниже порога. Остальные варианты дали от 0 до +5 % или ухудшили показатели. По задержке запас большой: p95 160–230 мс, у части вариантов с RRF 350–500 мс.

## Реранкеры на CPU (проверено после миссии)

По вашей просьбе проверил реранкеры на CPU. Сначала выяснилось, что базовый замер миссии шёл на заглушке hashing, а в проде эмбеддер `multilingual-e5-small`. Поэтому все реранкеры измерены поверх настоящего e5 на тех же 90 запросах (корпус: снимок репозитория вместе с `data-tables/`).

| Вариант | precision@5 | recall@8 | MRR | задержка поиска p95 |
|---|---|---|---|---|
| e5-small, без реранкера | 0,227 | 0,247 | 0,350 | 123 мс |
| + jina-reranker-v1-tiny-en (встроен в образ) | 0,200 | 0,209 | 0,308 | 3,7 с |
| + ms-marco-MiniLM-L6-v2 | 0,162 | 0,205 | 0,280 | 5,0 с |
| + Horizon-Labs multilingual-reranker-small (int8) | 0,193 | 0,199 | 0,335 | 13,8 с |

- **Все три реранкера ухудшают качество** на этом наборе и добавляют секунды. Это совпадает с записью в `.env.example`: на gold-наборах маленькие CPU-модели ранжировали хуже, чем без реранкера.
- **bge-reranker-v2-m3 на CPU не годится.** `reranker-service` я поднял на CPU (ONNX fp32): даже 10 фрагментов по 800 символов не укладываются в его внутренний лимит 15 с. По данным карточки ettin-reranker, bge-v2-m3 даёт около 6 пар в секунду на CPU, то есть 40 кандидатов занимают 6–7 с и больше. Контейнеры остановлены.
- **В `.env` проекта reranker-service выбрана модель Qwen3-Reranker-0.6B**, а в томе лежит только bge-v2-m3. При моём запуске я подставил bge через временный override. Сам `.env` не менял.
- **e5-small — эмбеддинг-модель, а не реранкер.** Она уже работает в проде (`RETRIEVAL_EMBEDDER=local`), реранкер в проде выключен (`RETRIEVAL_RERANKER=none`).

Оговорки: замеры шли на занятом процессоре (рядом работали Worker и сам замер), поэтому абсолютные задержки завышены. Набор silver: «правильными» считаются файлы, которые прогон потом открыл, а реранкер оценивает близость текста, так что набор может занижать пользу реранкера.

## Эксперименты миссии на e5 (2026-10-29)

Те же варианты, что в миссии, но поверх настоящего e5-small (раньше шли на hashing). База: P@5 0,227, R@8 0,247, MRR 0,349, p95 123 мс. Порог принятия: P@5 не ниже 0,272 и R@8 не ниже 0,217.

Вывод: на e5 ни один вариант не проходит порог, как и на hashing. Лучший по P@5 (0,240) теряет в recall, остальные в пределах шума. Менять параметры поиска не нужно.

## Выводы

1. Прирост от реранкера на CPU в разумное время мы не получили. Поэтому реранкер лучше оставить выключенным.
2. Веса слияния и размер фрагмента дают не больше +10 % к precision с потерей recall. Улучшать их на hashing-базе нет смысла: надо повторить эксперименты на e5.
3. Исходная проблема (точность Worker 8,6 %) не решена. Из метрик неясно, мешает ли поиск Worker'у: на живых прогонах эффект search gate не измерялся.

## Что не сделано и риски

- Эксперименты (а–д) измерены с hashing-эмбеддером. Для прода они не вполне показательны.
- Корпус двух замеров разный (рабочий каталог против снимка), поэтому база hashing (0,209) и база e5 (0,227) напрямую не сравниваются.
- Изменения не закоммичены: `search_cli.py`, `usage.py` и тесты. Записи в `CHANGELOG.md` пока нет.

## Что предлагаю дальше

1. Эксперименты повторены на e5 (раздел выше): результат тот же, параметры не меняем.
2. Включить `AHAWR_SEARCH_SKIP_PATH` на несколько миссий и сравнить по новому `usage` до и после.
4. Коммит и пуш версии 0.12.0 (новые функции) по вашей команде.

## Команды оператора

```bash
cd retrieval-service
ahawr-retrieval-eval run --dataset real --config eval/configs/hybrid-symbol-e5-local.json --out /tmp/rag_eval --freshness-mode verify
```

Search gate включается переменной `AHAWR_SEARCH_SKIP_PATH=1` в окружении Worker. Процедура сравнения до и после на живых прогонах: `docs/rag-quality.md`, раздел «Live comparison».
